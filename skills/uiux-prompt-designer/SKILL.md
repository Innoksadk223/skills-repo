# UI/UX 提示词设计器

只生成可复用的 UI/UX 规则模板和风格配置，不直接设计、实现或审查界面。模板的规则与输入约定自包含，但不含完整产品任务；下游仍需另行提供产品需求。

## 核心规则

- 优先级：当前明确要求 > 项目或平台约束 > 已保存风格 > 可靠推断 > 中性默认。
- 九组维度仅为内部覆盖检查，不规定采访轮数。路线 A 合并相关缺口聚焦确认；路线 B 正常路径集中一次批量确认。直接采用已明确内容，不重复确认，不适用项跳过。
- 产品名、品牌、具体页面、业务内容和单次流程是一次性内容，只在需求摘要中报告；最终提示词和风格 JSON 只保留可复用规则。
- 不预设流行风格，只按用途组合兼容规则；平台规范、可访问性、清晰状态、响应式和真实内容不因审美风格而取消。
- 保留 `implementation` 与 `visual` 两种模式；模式决定交付要求及规则表达，不改变双路线。提示词必须自包含，不依赖当前对话、本技能或生成时的源文件。
- 审美方向已确认且来源明确的新风格自动保存；已加载风格默认只复用，不因本次覆盖创建变体。未确认草稿不落盘。

## 审美确认：先理解，再转译

两条路线共用：提取用户描述或观察证据 → 概括审美意图 → 必要时提出候选解释 → 用户确认或纠正 → 转译视觉规则。此过程并入路线的正常确认，不新增全量问卷或状态文件。

- 区分三个层次：整体想给人的感受；形成该感受的可见特征；用户希望跨任务保留的核心。描述已经清楚的部分直接采用，不重复确认；只核实新增解释或会改变结果的分歧。
- 用户不必知道风格名称。名称仅作辅助索引：有可靠依据时可说明接近某种已有风格；自创或混合审美用描述性名称，不杜撰流派归属，也不为了分类删掉用户偏好。
- 有实质歧义时，给出 2–3 个简短、可感知的效果对照，并标为候选理解；无歧义不强造选项。不让用户在术语清单中猜答案，也不以“推荐”冒充已确认偏好。
- 把抽象感受转译为形状与线条、色彩关系、明暗与体积、材质表面、布局、排版和密度等可见关系；只展开相关维度。风格名与形容词可作补充，不能替代这些规则。圆角、阴影数值等低影响细节可沿已确认方向和平台约束处理。
- 审美推断不授权编造产品功能、主要操作、信息架构、关键流程、业务文案或数据；模板不需要的具体内容不追问，下游执行所需的关键缺口也不擅自填补。
- 可见事实、候选解释、用户已确认偏好分别记录；确认前的草稿不保存为风格。文字走查只核对规则表达，不保证所有模型正确理解，更不代表实际视觉稿或界面效果已验证。

## 模块 1：选择路线并预填

1. 提取用户请求、图片、目标模式、明确偏好、禁止项和已指定的本地风格。
2. 用户要直接搭建、修改、设计或审查 UI 时转交执行能力；粘贴成品提示词文本要求倒推时说明不支持，不转入路线 A 或 B。
3. 指定已有风格时，先从 `~/.agents/uiux-prompt-styles/` 加载；唯一匹配直接使用，多个不同匹配请用户选择，无匹配则说明，按新风格流程确认后再保存。
4. 再按输入选择路线：有成品界面图片或截图，读取 [路线 B：识图倒推](references/route-b-reverse-ui.md)；只有文字需求，读取 [路线 A：文字需求与聚焦确认](references/route-a-interview.md)。
5. 风格锁定的是源文件和未覆盖条目，不是禁止本次调整。用户选定的风格作为已明确基线，不逐组重问；只确认模板所需的模式、约束和实质审美分歧。
6. 当前明确要求仅覆盖冲突条目，形成此次提示词，不改源文件；未覆盖条目的措辞与相对顺序保持稳定。覆盖正向规则时同步检查 `avoid`，避免两边要求相反；必要取舍不明确则先确认。未加载风格时同样直接采用已明确内容。

模式判断：

- `implementation` 交给编码或前端实现模型；`visual` 交给视觉稿、界面图或原型模型。
- 模式明确时直接采用；路线 A 只在模式有歧义时询问，路线 B 在集中确认中处理。不能因静态截图推定要实现代码。
- 用户要求两种模式时分别生成，不把工程语法混入 `visual`。

不先展示空模板；按缺口进行确认。输出契约见模块 3、5。

路线 A 模板必要信息齐全、审美解释获确认后进入模块 2、3；路线 B 在集中确认前完成模块 2，确认或修正后再做一致性检查，齐全且无冲突才进入模块 3；新关键缺口或互斥要求按路线 B 暂停处理。

## 模块 2：处理冲突与边界

以下只是检查线索，不因风格词不同就否定混合审美。仅当同一对象、同一层面的要求无法同时成立或会破坏明确目标时，才需要取舍。

- 官方设计系统和平台规范决定组件行为与可访问性，审美风格只调整兼容的表面层。
- 极简与高密度按用途收敛；大量装饰与极简、深色与锁定浅色品牌、平台原生与强纹理或重拟物、强 3D 与高效率后台等显式冲突需要取舍。
- 强玻璃、模糊、颗粒或纹理不得牺牲对比度、可读性、性能或平台一致性。
- Scrollytelling、持续背景动画和强视差必须提供 `prefers-reduced-motion` 静态降级；不得靠低对比度、移除焦点、仅 hover 或缩小触控目标维持风格。
- 参考界面的商标、专有文案、业务数据和可识别品牌组合是一次性内容，不进入提示词或风格文件。

两个显式高影响要求冲突时，路线 A 聚焦确认必要取舍；路线 B 将冲突、建议取舍和修正方式并入集中确认。修正后重新检查，不以确认次数为由跳过冲突。低影响冲突沿已确认方向处理，必要时简短说明；处理后只以最终确认结果为准。

## 模块 3：组装通用自包含提示词

每份成品放入一个连续的 `text` 代码块，包含全部规则、执行模式、输入约定与适用约束；标题语义固定，栏目按需出现。以下是组装说明，不是可直接交付的占位模板：

| 标题 | 使用条件与内容 |
| --- | --- |
| `[设计规则]` | 核心：已确认的视觉关系、色彩、排版、布局、图标、组件与材质；不以风格名代替规则。 |
| `[体验规则]` | 核心：按模式表达导航、状态、反馈和可访问性；visual 描述能看到的状态与提示，implementation 才要求实现行为。 |
| `[内容规则]` | 按需：可复用的信息层级、内容密度、真实内容、空态和错误态规则。 |
| `[交付规则]` | 核心：明确 implementation 或 visual 及对应的边界、交付和验证；可靠视觉模型参数如需提供，也完整放在本节内。 |
| `[禁止事项]` | 按需：适用的反模式和风格禁项，全部写在本块内。 |
| `[任务]` | 核心：声明这是通用规则模板；要求下游另行提供产品任务、页面范围与必要内容约束，收到后按规则执行，关键输入缺失时先询问，不编造产品。 |

省略没有实际内容的可选栏目，不写“无额外……”；不另设空参数栏。模板的输入约定是明确接口，不是指向本次对话的“见上文”。

两种模式分别补充：

### implementation

- 先检查现有项目，保留技术栈、设计令牌、组件库、路由、数据和品牌资产，不重建脚手架；只改授权文件，未指定技术栈时沿用项目。
- 覆盖需要的 default、hover、focus-visible、active、disabled、loading、error 和 success 状态。
- 明确桌面、平板、手机行为，以及键盘导航、语义、标签、对比度、触控目标和减少动效要求。
- 保留性能、真实内容、运行方式和最小验证；不增加未授权依赖、后台、登录、数据库或部署。

### visual

- 使用可见结果描述：设备视口、层级、构图、网格、留白、密度、色彩、排版、图标、材质表面、光线及组件位置关系。模板约定由下游任务提供目标设备与视口，未指定时先确认，不预造某个页面布局。
- 只要求呈现任务需要的可见状态，如选中标识、焦点轮廓、错误说明、空态提示；不凭一个静态画面声称已实现键盘导航、动效、响应式或交互流程。需展示多个视口或状态时，由下游任务指定范围并分别绘制。
- 保留文字清晰、层级可辨、状态不只靠颜色区分等可见底线；技术和行为要求不硬塞进生图指令，不用 CSS 属性、代码或性能术语替代画面描述。
- 使用真实语境内容，无数据时只用明确标记的中性示例，不编造商业证明。排除乱码、重叠和不可读小字；设备外壳和假浏览器框默认不加，用户明确需要展示情境时例外。
- 仅在用户指定视觉模型时添加可靠参数，不伪造专属语法；不把视觉稿验收冒充可运行界面验收。

组装时剔除一次性内容及路线 B 的证据与推断依据；不写角色设定、占位符或无关元指令，也不让设计规则与禁止事项要求同一特征。

已加载风格按固定映射取出适用条目：`principles` → `palette.colors`、`palette.rules` → `typography` → `layout` → `surfaces` → `components` 依序写入 `[设计规则]`；`interaction` → `motion` → `accessibility` 依序写入 `[体验规则]`；`implementation_hints` 仅在 implementation 写入 `[交付规则]`；`avoid` 并入 `[禁止事项]`。`fit` 用于判断适用性，不把其场景例子当作当前产品任务。

- 同一模式下，未覆盖的适用条目逐条保留文字和相对顺序，不为新任务润色整个风格段；当前明确要求只替换冲突条目及受影响禁项。必要的平台底线与风格冲突时说明取舍，不静默改变风格。
- visual 只纳入能描述可见结果的条目；纯行为、动效实现或工程条目不因原样复用而硬塞进生图指令。说明被模式排除的条目，不改源字段；若转译需要新设计决定，将候选可见表达并入正常审美确认，不静默改写。可见底线仍保留，不能承诺静态稿已经实现不可见行为。
- 通用模板按用户确认的跨任务审美核心保留配色、布局与组件规则，不剔除整类字段；一次性页面、品牌与未经确认的场景安排不泛化为风格。块外简述实际覆盖或模式筛选，源文件默认不改。

## 模块 4：保存或复用风格

仅在审美方向已确认、可复用规则来源明确后，按以下规则保存或复用 UTF-8 JSON；未确认草稿不落盘：

1. 使用 `~/.agents/uiux-prompt-styles/<kebab-case-id>.json`；目录不存在时创建。
2. `origin` 只记录 `user`、`reference`、`inferred` 或用户提供的来源；不保存一次性内容、项目路径、文件名或路线 B 证据。
3. 已加载风格即使有本次覆盖或模式筛选，默认仍不写文件、不创建变体，报告源路径及实际覆盖。只有用户明确授权更新原风格时才修改对应字段，其他字段不变；明确要求另存时才另存。确为已确认的新风格且同名不同内容时沿用 `-2`、`-3` 变体机制，不把草稿、临时覆盖或两种模式当成新风格。
4. 保存失败仍交付提示词，并报告原因和未保存状态。

保持 `schema_version: 1` 和现有字段不变；没有内容的可选字段保持空值，不补造偏好：

- `材质质感和纹理` 写入 `surfaces`；组件形态与状态继续写入 `components`。
- `atmosphere` 仅为旧文件兼容保留，不进入需求单或提示词，新文件保持空数组。

```json
{
  "schema_version": 1,
  "id": "style-id",
  "name": "风格名称",
  "summary": "一句话描述",
  "origin": "user、reference、inferred 或来源说明",
  "fit": {"good_for": [], "bad_for": []},
  "principles": [],
  "palette": {"colors": [], "rules": []},
  "typography": [],
  "layout": [],
  "surfaces": [],
  "components": [],
  "interaction": [],
  "motion": [],
  "atmosphere": [],
  "accessibility": [],
  "implementation_hints": [],
  "avoid": []
}
```

## 模块 5：输出格式

使用与用户相同的语言，除非用户指定其他语言。

- 最终交付以一块连续的 `text` 代码块为主体；规则、模式、下游输入约定、适用负向约束和可靠参数全部在块内。执行所需的验收要求也在 `[交付规则]`，不要求另复制外层清单。
- 用户要求两种模式时，分别交付完整代码块，一份一块；不把工程指令混入 visual，不用“其余同上”引用另一份。
- 块外仅补充必要假设、限制、本次风格覆盖摘要，以及保存／复用的绝对路径或失败原因；没有内容的栏目省略，不重复方向摘要、避免事项、空参数栏和整份验收清单。
- 路线 B 的证据与候选解释在确认阶段展示，不进入成品；块内明确通用模板仍需另给产品任务。风格 JSON 写文件，不要求用户复制它才能使用规则。

## 质量检查

输出前确认：

- 路线 A 仅确认实质缺口，已明确和不适用内容未重复采访；维度清单仅用于覆盖检查。路线 B 的证据与集中确认按其参考文件执行。
- 静态截图无法证明的交互、动效、响应式、技术栈和完整可访问性没有被写成可见事实；一次性内容未进入提示词或风格文件。
- 每份成品只有一个连续 `text` 代码块，包含全部规则、模式、下游输入约定、负向约束及适用参数，无空栏目或块外依赖；明确通用模板不含具体产品任务；正负向无冲突。
- 模式与执行器匹配：`implementation` 保留项目、文件、状态、响应式、可访问性、性能和验证边界；`visual` 保留视口、布局、层级、材质质感和纹理、关键状态、真实内容和负向视觉要求。
- 视觉与材质规则符合用途、密度和平台，材质效果不牺牲可读性或性能，也不虚构业务内容或扩展；风格文件兼容 `schema_version: 1`，且已报告路径或失败原因。
- 复用时未覆盖的适用条目保持原文及相对顺序，本次覆盖与受影响禁项一致；模式不适用项有说明而未改源字段，源文件未被默认改写，未产生无意变体。
