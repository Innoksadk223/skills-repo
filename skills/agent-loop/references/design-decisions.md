# Agent Loop 设计决策记录

2026-06-10 grill-me 会话产出。8 个问题逐层递进，从场景到实现路径。

## Q1: 适用场景
代码 + 研究/写作 + 复杂多步骤任务（≥3 环节）。不做纯通用 loop。

## Q2: 验收方式
**选 C**（结构化 checklist）。不另起 agent 当裁判（B 太贵），不让 agent 兼裁判（A 盲区大）。量化标准 + worker 自检 + 主 agent 看自检报告。

## Q3: 问题诊断和 prompt 重写
**选 A**（合并，主 agent 兼任）。分离（B）多一步调用，token 代价大于收益。主 agent 已掌握任务全貌和验收标准，不需要另起炉灶。

## Q4: Worker 并行策略
**动态判断权给 agent**。依赖关系存在时串行，无依赖时并行。不硬编码并行/串行。

## Q5: 规划深度
**动态，但必须输出主要步骤 + 边界条件**。不做纯粗规划（容易跑偏），不做过度细规划（烧 token）。计划 token 占比 ≤ 30% 单轮总预算。

## Q6: 终止条件
**3 轮硬上限 + 10% 提升阈值**。3 轮不达标交付当前结果 + 未达标清单。连续 2 轮提升 < 10% 提前终止。

## Q7: 资源调整
模型选择、并发数、上下文注入量、技能调用——全部动态。不同任务不同配置。

## Q8: 实现路径
最初讨论了三方案（纯 Skill / delegate_task 编排 / 混合），但在用户追问"按最早 agent loop 定义给建议"后收敛为**单 agent 内嵌 loop**。核心理由：
- 经典 ReAct 就是一个 LLM 一个上下文窗口的循环
- 多 agent 是上下文隔离工具，不是默认架构
- spawn 子 agent 的触发条件是"信息量淹没主 agent 全局判断"，不是"任务可以拆解"
