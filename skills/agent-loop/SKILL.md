# Agent Loop

**“不要给 Agent 写 Prompt，写 Loop——让 Loop 给 Agent 写 Prompt。”**

Agent Loop 是一个确保高质量产出的通用工作流。其本质是建立一个内部监督机制：主 Agent 负责执行和迭代（ACT），子 Agent 负责审核和写 Prompt（AUDIT），两者基于共享文件系统形成闭环。

## 父子 Agent 交互机制（核心设计）
为了实现“可持续对话”且避免 Token 浪费，父子 Agent 必须遵循以下交互协议：
1. **状态互通（Worktree 共享）**：主从 Agent 之间必须通过本地文件系统（如 `state/` 目录）共享状态。需求、计划、代码产出均落盘，**绝不在会话中互相大段复制黏贴内容**。
2. **会话存活（Stateful Subagent）**：
   - 主 Agent 可通过**后台终端（Terminal PTY / Background Process）**挂起一个存活的子 Agent 交互进程（如启动一个交互式 CLI Agent）。
   - 或者通过编写并触发一个**维持上下文历史的自动化审查脚本（Hook / Script）**作为子 Agent 的载体。
3. **极简心跳交互**：首轮子 Agent 读取完背景文件后，后续轮次主 Agent 只需要向存活的子 Agent 发送极简心跳信号：“已按你的 prompt 修改完毕，请重审最新文件”。子 Agent 验证后直接输出下一个“修正 Prompt”或“PASS”。

## 核心流程（必须严格按顺序执行）

### 1. PLAN（计划与 Intake）
- **先想后做**：不管是否调用专门的 planning 技能，必须先与用户进行苏格拉底式提问。
- **明确要素**：澄清用户真实需求、目的、验收标准以及**循环的终止条件**（如最大轮数、资源限制、超时设定）。
- **本地落盘（子 Agent 的准绳）**：将上述明确后的目的、验收标准和终止条件，**强制写入本地约定文件**（如 `state/loop_plan.md`）。**子 Agent 必须能够看到并读取此文件，以此作为它一切审核行为和终止判断的唯一依据。**

### 2. ACT（主 Agent 执行）
- 主 Agent 根据写好的 `loop_plan.md`，在**当前主会话中直接执行任务**，调用相应的工具（写代码、建文件、执行命令等）。
- 必须产出实质性的内容（文件、代码、完整的文档等），并落盘保存到约定目录。

### 3. AUDIT（分派审核子 Agent）
- **唤醒/分派**：主 Agent 初步产出后，分派并唤醒那个**可持续交互**的审核子 Agent。
- **初始指令**：主 Agent 第一次呼叫子 Agent 时，指令其：“请读取 `state/loop_plan.md` 了解目的与终止条件，并审查我刚刚生成的本地代码产物”。
- **审查与输出**：子 Agent 不亲自改代码，它根据 plan 文件的约束审查产出。若发现缺陷或不符，**针对性地写出可供主 Agent 直接执行的“修正 Prompt”**（可以写入 `state/feedback.md` 或直接作为终端输出返回给主 Agent）。

### 4. LOOP（迭代循环）
- 主 Agent 收到子 Agent 提供的“修正 Prompt”后，直接将此 Prompt 作为下一步的工作指令，继续在主会话中修改代码。
- 每次修改完成后，主 Agent 仅需向持续存活的子 Agent 发送极简消息：“已更新，请按 plan 继续审核”。
- 此过程循环往复，直至子 Agent 输出 `PASS`，或子 Agent 发现已达到 `loop_plan.md` 中设定的终止条件（如判定已达最大修正轮数）。

### 5. VERIFY（最终验收）
- 循环结束，子 Agent 审核通过（或强行终止）后。
- 主 Agent 亲自将最终成果与 `state/loop_plan.md` 进行最后一次比对校验。
- 确认符合目标后，直接向用户交付最终结果。

## 关键要求
- **不打扰用户**：在循环迭代期间，主 Agent 和子 Agent 内部解决所有技术细节，不要因中间状态频繁向用户提问。只有在触及终止条件死锁时才向用户求助。
- **主从倒置**：在这个 Loop 中，主 Agent 是干活的工人，受 Prompt 驱动；子 Agent 才是 Prompt 的制定者、挑剔的评审官。
