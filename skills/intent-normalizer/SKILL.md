# Intent Normalizer

## 核心原则

- 先还原目标，再处理方案。用户说的是线索，不一定是最终需求。
- 化身对应领域专家，但不要把专业术语直接丢给非专家用户选择。
- 只补齐执行必需的信息，不替用户扩需求。
- 能安全假设的先明示假设；会改变路线、成本、风险或交付物的问题才追问。
- 如果用户方案明显不适合目标，先指出问题，再给出更合适的任务表述。
- 规范化不是交付终点。契约足够清楚时，立即进入执行；只有关键缺口会改变结果时才暂停问人。

## 专家模式

触发本技能后，先在内部切换到对应领域专家视角，再规范化用户描述。专家模式不是单独交付物，不要输出“我是某某专家”的表演式话术。

专家模式必须完成四个判断：

1. **领域镜头**：判断主领域和必要交叉领域，选择应采用的专家角色。
2. **表象翻译**：把用户的生活化说法翻译成领域里的真实需求。
3. **专家判断**：识别用户可能混淆的目标、方案、交付物、约束或风险。
4. **用户友好确认**：只有答案会改变路线时，才用非术语问题确认。

专家模式的结果应体现在更准确的默认假设、纠偏、交付物选择和验收标准里。不要炫技、不要堆术语、不要替用户扩需求。

## 先做输出决策

本技能的第一步不是写契约，而是决定用户现在需要看到什么。

按以下优先级判断，只选会改变下一步的最小动作：

1. **安全或不可逆**：删除、覆盖、公开发布、付费调用、修改系统环境等，先暂停确认。
2. **方向明显错误**：用户给的方案会偏离目标，先用一句话纠偏，再给更合适的执行路线。
3. **存在真实路线分叉**：多个合理方案会影响成本、体验或维护负担，用生活化效果描述选项，让用户选。
4. **用户要求先对齐**：用户明确要先梳理、评估可行性、确认范围/成本/交付物时，只展示会影响决定的精简契约或选项摘要。
5. **关键缺口未补齐**：答案会改变交付物或执行路径时，只问 1-3 个效果题。
6. **可安全假设**：明示默认假设，内化任务契约，直接进入执行。

不要默认展示完整契约。完整契约是给 Agent 对齐执行用的，不是用户每次都需要看的交付物。

## 轻量流程

按顺序在脑中完成四步；日常短任务不要强制写 `state/` 文件。

1. **识别**：进入专家模式，区分用户字面请求、真实目标、主领域、交叉领域、专家角色、隐含约束和盲目执行风险。
2. **筛选**：把缺口分成五类：安全确认、需要纠偏、路线选择、必须追问、能安全假设。不要把好奇心当成澄清问题。
3. **规范化**：把用户原话改写为可执行任务契约，让后续 AI 或当前 Agent 可以直接执行。
4. **推进**：若契约已足够执行，直接开始下一步；若必须追问，只问最少问题并暂停。

复杂、多轮、需要恢复的任务才落盘。落盘时使用独立命名空间，例如 `state/intent-normalizer/<intent_task_id>/task_contract.md`；用户原始请求变化时必须创建新的 `intent_task_id`，不得复用旧任务状态。

## 判断规则

- **直接执行**：真实目标、交付物、约束和验收标准已经足够清楚；明示默认假设后继续执行。
- **先问再做**：缺失信息会改变路线、成本、风险、交付物或不可逆动作。
- **先纠偏再做**：用户提出的方案明显不是达成目标的好路径；先用一句话点破，再给可执行替代路线。替代路线只有一个明显最优解时，直接按它执行；存在真实取舍时再让用户选。
- **给路线选择**：存在多个合理方案且取舍会影响体验、成本或维护负担；用效果和代价描述选项，不要求用户懂术语。选项最多 3 个，必须说明推荐项。
- **精简对齐**：用户要先确认范围、成本、交付物、可行性或协作边界时，输出精简契约；若下一步已经明确，继续执行，否则停在需要用户确认的选择点。
- **不触发本技能**：用户只是闲聊、解释概念，或给了一个已经明确的单步命令。

## 缺口分级

| 缺口类型 | 处理方式 | 例子 |
|----------|----------|------|
| 不影响首版结果 | 写入默认假设，继续执行 | 未指定配色，先采用与目标一致的默认风格 |
| 影响路线或成本 | 追问 1 个效果题 | “只是自己用，还是给多人长期用？” |
| 影响安全或不可逆动作 | 暂停确认 | 删除、覆盖、公开发布、付费调用 |
| 方案目标混淆 | 先纠偏再改写 | 用户要“做系统”，真实目标可能只是整理流程 |

## 提问方式

面向非专家用户时，不问术语题，问效果题。

- 不问：“你要前端还是全栈？”
- 改问：“只是浏览器里打开的页面，还是需要别人登录、保存数据？”
- 不问：“你要 SaaS 架构吗？”
- 改问：“这是自己临时用，还是要给多人长期使用？”

问题必须同时满足：

- 答案会改变下一步做法。
- 用户能凭生活经验回答。
- 每个问题附一句“为什么这会改变执行”。

避免一次性盘问。超过 3 个问题时，先做分阶段确认：只问当前阶段最关键的问题。

## 压力自检

输出前用这几条快速拦截常见误用：

- **是否只复述了表象？** 如果用户只说愿望、感受或粗糙方案，先用专家视角翻译成真实目标和交付物，再执行。
- **是否在契约表演？** 如果用户要的是结果，而不是任务分析，不展示完整契约；用内部契约直接推进。
- **是否在过度追问？** 如果答案不会改变首版交付物、成本、风险或不可逆动作，写成默认假设并继续。
- **是否在问术语题？** 如果问题需要用户理解技术分层、架构名词或专业流程，改成效果、使用场景或限制条件。
- **是否纠偏后卡住？** 如果只有一个更合理路线，说明并执行；只有存在真实取舍时才停下来让用户选。

## 输出模板

需要追问时，先输出简短问题并暂停：

```markdown
我先确认 [1-3 个问题]，因为这些答案会改变最终做法：

1. [问题]
   原因：[为什么这个答案会改变执行]
```

可以继续时，输出或内化下面的任务契约：

```markdown
# 规范化任务契约

## 用户真实目标

[一句话说明用户真正想达成什么]

## 专家视角

- 领域：[主领域；必要时写交叉领域]
- 角色：[应化身的专家身份]
- 表象翻译：[用户生活化说法在该领域里的真实含义]
- 关键判断：[1-3 条]

## 可执行任务

- 交付物：
- 范围：
- 输入：[用户已提供的材料、文件、上下文；没有则写“无”]
- 输出：[最终交付物的具体形态、文件或回复]
- 约束：
- 不做：

## 默认假设

- [可以安全采用的假设]

## 验收标准

- [ ] [可判断的完成标准]

## 风险与未确认项

- [不阻塞执行但需要说明的风险]

## 下一步

[直接执行 / 先确认问题 / 给出路线选择 / 暂停]
```

使用规则：

- 用户只需要最终结果时，不必完整展示契约；把契约作为内部执行依据即可。
- 用户需要对齐范围、成本或交付物时，只展示会影响决定的精简契约。
- 契约展示后不要停在“这是规范化结果”；若下一步明确，继续调用相应工具或 skill。
- 后续执行中发现契约假设不成立，先更新契约，再继续或追问。

## 示例

用户：我想要设计一个网页，会动的那种。

规范化：

```markdown
## 用户真实目标

做一个能在浏览器打开、视觉上有动效和交互感的网页原型。

## 专家视角

- 领域：网页原型设计 / 前端实现
- 角色：网页设计师 + 前端工程师
- 表象翻译：“会动”通常指页面有动效、转场或交互反馈，不等于要做复杂应用或动画引擎
- 关键判断：
  - “会动”大概率指页面动效，不代表复杂应用
  - 用户没提登录、数据库、后台，所以不默认扩展
  - 首版适合做 HTML + CSS + JavaScript 单页网页

## 可执行任务

- 交付物：一个本地可打开的静态单页网页
- 范围：布局、视觉风格、CSS 动效、少量 JavaScript 交互
- 输出：HTML、CSS、JavaScript 文件
- 不做：账号系统、后台接口、数据库、上线部署

## 默认假设

- 先做展示型原型；如需保存数据或多人登录，再升级方案。

## 验收标准

- [ ] 页面能正常打开
- [ ] 有明确视觉主题
- [ ] 至少包含 2-3 处动效或交互
- [ ] 不需要服务器也能运行
```
