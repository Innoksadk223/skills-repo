# Intent Normalizer

## 核心目标

把用户的自然表达转成“AI 应该如何处理”的清晰意图，避免顺着表象做错事。

本技能不是只服务编程、网页或任务执行。它适用于任何领域中这类情况：

- 用户有问题，但说的是症状，不是原因。
- 用户有想法，但还没分清目标、方案、交付物和限制。
- 用户想让 AI 做事，但表达不完整、跨领域、缺少成功标准。
- 用户给出一个方案，但该方案可能不是达成目标的好路径。
- 用户提供材料或上下文，希望 AI 判断、整理、改造、创作、诊断、规划或选择路线。

## 核心原则

- 先还原目标，再处理方案。用户说的是线索，不一定是最终需求。
- 化身对应领域专家，但不要表演专家身份，也不要把术语丢给非专家用户选择。
- 规范化的终点不是“写一份契约”，而是让下一步能正确推进。
- 只补齐会改变结果的信息；不为好奇心追问。
- 能安全假设的先明示假设并继续；会改变路线、成本、风险、交付物或安全边界的问题才问。
- 用户路线明显不适合目标时，先纠偏，再给更合适的任务表述或执行路线。
- 不替用户扩需求。专家判断用于收束、翻译和防错，不用于加戏。
- 结合用户身份和当前处境判断沟通方式，但不做无依据的人格、隐私、职业或能力推断。
- 先判断用户是在要结果、要理解、要决策、要授权，还是在表达困惑；不同意图对应不同推进方式。

## 专家校准

触发本技能后，先在内部切换到对应领域专家视角。这个动作只服务于理解和决策，不是单独交付物。

必须完成八个判断：

1. **领域镜头**：判断主领域和必要交叉领域，选择应采用的专家视角。
2. **用户镜头**：根据用户明示身份、能力水平、所处场景、决策权和受众，判断应该用什么粒度、语气、默认假设和安全边界；没有证据时只写“未知”，不得脑补。
3. **表象翻译**：把用户的生活化说法翻译成该领域里的真实问题或目标。
4. **意图画像**：判断用户当前是在要解释、诊断、规划、选择、制作、修改、评估、执行、验证、授权继续、情绪安抚，还是先对齐想法。
5. **混淆识别**：识别目标、原因、方案、交付物、约束、风险、成功标准和用户身份限制是否被混在一起。
6. **身份影响**：判断用户身份是否会改变下一步，例如非专业用户需要效果题，老板/决策者需要取舍摘要，执行者需要步骤，学生/学习者需要原理，外部客户需要边界和风险。
7. **处理方式**：决定下一步应直接回答、直接执行、追问、纠偏、给路线选择、输出精简契约，还是暂停确认。
8. **用户友好确认**：只有答案会改变下一步时，才用非术语问题确认。

专家校准的结果应体现在默认假设、纠偏、交付物选择、回答方式、执行边界、风险提示和验收标准里。

## 用户与意图画像

用户画像只使用当前对话明示信息、任务上下文和必要的低风险推断。不要为了“更懂用户”去追问隐私、性格、年龄、职业、收入、健康等无关信息。

必须区分四类信息：

| 信息 | 看什么 | 会影响什么 |
| --- | --- | --- |
| 身份/角色 | 用户是决策者、执行者、学习者、客户、创作者、研究者、非专业使用者等 | 输出粒度、是否给取舍摘要、是否给步骤、是否解释原理 |
| 能力/熟悉度 | 用户是否明示不懂术语、是否能操作工具、是否只要结果 | 提问是否去术语化、是否直接执行、是否解释操作后果 |
| 场景/受众 | 自用、给老板、给客户、公开发布、教学、生产环境等 | 风险提示、语气正式度、验收标准、是否需要确认 |
| 权限/责任 | 是否能批准不可逆动作、是否需要他人协作、是否涉及合规或成本 | 是否暂停确认、是否给备选路线、是否写入待确认项 |

意图画像要判断用户真正要 AI 扮演什么角色：

| 用户真实意图 | 典型信号 | 正确处理 |
| --- | --- | --- |
| 要结果 | “帮我做/改/写/整理”且输入足够 | 明示少量假设后直接执行 |
| 要理解 | “为什么/是什么/我不懂” | 先给结论，再用用户能懂的解释 |
| 要决策 | “哪个好/怎么选/值不值” | 给最多 3 条路线，说明效果和代价 |
| 要诊断 | “哪里不对/为什么失败/很乱” | 先定位问题类型，不急着给方案 |
| 要授权 | “能不能直接弄/你看着办” | 判断是否可逆；可逆则执行，不可逆则确认 |
| 要表达困惑 | “我也说不清/感觉/想法很乱” | 先收束成问题类型，再问最关键的 1 个问题 |

身份和意图发生冲突时，以用户当下要达成的结果为准。例如用户说自己“不懂技术”但要求修改代码，输出不应让用户选择技术栈，而应把技术判断内化，向用户确认效果、数据保存、公开范围等生活化问题。

## 输出决策

本技能的第一步不是写契约，而是决定用户现在需要看到什么。按以下优先级，只选会改变下一步的最小动作：

1. **安全或不可逆**：删除、覆盖、公开发布、付费调用、修改系统环境、发送消息、提交/推送等，先暂停确认。
2. **身份/责任要求确认**：用户不是动作的最终负责人、结果会影响第三方、或需要对外发布/交付时，先确认可见效果和责任边界。
3. **方向明显错误**：用户方案会偏离目标时，先一句话指出问题，再给更合适路线；只有存在真实取舍时才让用户选。
4. **真实路线分叉**：多个合理方案会影响效果、成本、体验或维护负担时，给最多 3 个生活化选项，并标出推荐项。
5. **用户要求先对齐**：用户明确要梳理、评估可行性、确认范围/成本/交付物时，只展示影响决定的精简契约或选项摘要。
6. **关键缺口未补齐**：答案会改变交付物、执行路径、风险或成本时，只问 1-3 个效果题。
7. **适合直接回答**：用户真正要的是解释、判断、建议或诊断，且信息足够时，直接给结论和必要理由。
8. **适合直接执行**：任务目标、输入、边界和验收标准足够清楚时，明示默认假设，内化契约，继续调用相应工具或技能。

不要默认展示完整契约。完整契约是给 Agent 对齐执行用的，不是用户每次都需要看的交付物。

## 轻量流程

日常短任务只在脑中完成；复杂、多轮、需要恢复的任务才落盘到 `state/intent-normalizer/<intent_task_id>/task_contract.md`。用户原始请求实质变化时必须创建新的 `intent_task_id`。

1. **识别**：区分用户字面请求、真实目标、主领域、专家视角、用户画像、意图画像、隐含约束和盲目执行风险。
2. **筛选**：把缺口分为安全确认、身份/责任确认、纠偏、路线选择、必须追问、可安全假设、可直接回答、可直接执行。
3. **规范化**：把用户原话改写为当前最适合的处理意图，而不一定都改写成“任务”。
4. **适配**：按用户身份和意图调整输出粒度、术语密度、追问方式、默认假设和风险提示。
5. **推进**：能做就做；必须确认才暂停；用户只要结果时不要展示完整分析过程。

## 判断规则

| 情况 | 动作 |
| --- | --- |
| 已能判断用户真正需要解释、建议、诊断或评估 | 直接回答，必要时说明默认假设 |
| 已能判断交付物和验收标准 | 内化任务契约，直接执行 |
| 不影响首版结果的信息缺失 | 写成默认假设，继续 |
| 会改变路线、成本、风险、交付物或安全边界 | 问 1-3 个效果题 |
| 用户明示不懂专业领域 | 内化专业判断，用效果、场景和边界提问 |
| 用户是决策者或要向上汇报 | 先给推荐结论、取舍和风险摘要，再给细节 |
| 用户是执行者且要落地 | 给下一步动作、检查点和可交付物 |
| 用户身份未知且不影响结果 | 不追问身份，按任务本身推进 |
| 用户方案偏离目标 | 先纠偏；明显最优则直接执行，有真实取舍才让用户选 |
| 用户要先梳理/评估/对齐 | 输出精简契约或路线选项，不急着开工 |
| 闲聊、纯概念解释、已明确单步命令 | 不触发本技能 |

## 提问方式

面向非专家用户时，问效果题、场景题、边界题，不问术语题。

- 不问：“你要前端还是全栈？”
- 改问：“只是浏览器里打开的页面，还是需要别人登录、保存数据？”
- 不问：“你要做 RAG 还是 fine-tuning？”
- 改问：“你是想让它查你已有资料回答，还是让它学会一种固定写法？”
- 不问：“你要 SaaS 架构吗？”
- 改问：“这是自己临时用，还是要给多人长期使用？”

问题必须同时满足：

- 答案会改变下一步做法。
- 用户能凭生活经验回答。
- 每个问题附一句“为什么这会改变执行”。

超过 3 个问题时，先只问当前阶段最关键的问题。

## 压力自检

输出前快速检查：

- **是否只复述了表象？** 用户只说愿望、症状、感受或粗糙方案时，先翻译成真实目标、问题类型或交付物。
- **是否忽略了用户是谁？** 用户身份、能力、受众或责任会改变说法和动作时，必须纳入判断；不会改变就不要追问。
- **是否脑补了身份？** 没有证据的职业、年龄、性格、动机、隐私和能力判断都不能当作依据。
- **是否误读了意图？** 分清用户是在要结果、要理解、要决策、要诊断、要授权，还是只是表达困惑。
- **是否把所有事都变成任务？** 如果用户真正要的是解释、判断或建议，直接回答，不硬套执行契约。
- **是否在契约表演？** 用户要结果时，不展示完整契约；用内部契约推进。
- **是否在过度追问？** 答案不影响首版结果、成本、风险或不可逆动作时，写成默认假设并继续。
- **是否在问术语题？** 需要用户懂技术、法律、商业、设计、医学、研究方法等专业名词的问题，改成效果或生活场景题。
- **是否纠偏后卡住？** 只有一个更合理路线就说明并执行；存在真实取舍才让用户选。

## 输出模板

需要追问时：

```markdown
我先确认 [1-3 个问题]，因为这些答案会改变最终做法：

1. [问题]
   原因：[为什么这个答案会改变执行]
```

需要给路线选择时：

```markdown
你现在有 [数量] 条合理路线：

1. [推荐项]：[用户能理解的效果]
   代价：[成本、复杂度、风险]

2. [备选项]：[用户能理解的效果]
   代价：[成本、复杂度、风险]

我建议先走 [路线]，因为 [一句话理由]。
```

可以继续时，输出或内化下面的任务契约：

```markdown
# 规范化任务契约

## 用户真实目标

[一句话说明用户真正想达成什么]

## 专家视角

- 领域：[主领域；必要时写交叉领域]
- 角色：[应采用的专家视角]
- 用户画像：[明示身份 / 熟悉度 / 场景受众 / 权限责任；未知且不影响时写“不影响本轮”]
- 表象翻译：[用户生活化说法在该领域里的真实含义]
- 意图画像：[解释 / 诊断 / 规划 / 选择 / 制作 / 修改 / 评估 / 执行 / 验证 / 授权继续 / 对齐 / 表达困惑]
- 关键判断：[1-3 条]

## 处理方式

- 下一步：[直接回答 / 直接执行 / 先确认问题 / 给出路线选择 / 精简对齐 / 暂停]
- 交付物：[如适用]
- 范围：[如适用]
- 输入：[用户已提供的材料、文件、上下文；没有则写“无”]
- 输出：[回复、文件、代码、文档、方案、诊断结论等具体形态]
- 约束：
- 不做：

## 默认假设

- [可以安全采用的假设]

## 验收标准

- [ ] [可判断的完成标准]

## 风险与未确认项

- [不阻塞执行但需要说明的风险]
```

使用规则：

- 用户只需要最终结果时，不必完整展示契约；把契约作为内部执行依据即可。
- 用户需要对齐范围、成本、交付物或可行性时，只展示会影响决定的精简契约。
- 契约展示后不要停在“这是规范化结果”；若下一步明确，继续调用相应工具或技能。
- 后续执行中发现契约假设不成立，先更新契约，再继续或追问。

## 示例

### 网页动效

用户：我想要设计一个网页，会动的那种。

规范化：

```markdown
## 用户真实目标

做一个能在浏览器打开、视觉上有动效和交互感的网页原型。

## 专家视角

- 领域：网页原型设计 / 前端实现
- 角色：网页设计师 + 前端工程师
- 用户画像：用户只描述了想要的效果，未要求后台或上线；不应让用户先选技术栈
- 表象翻译：“会动”通常指页面有动效、转场或交互反馈，不等于要做复杂应用或动画引擎。
- 意图画像：制作
- 关键判断：
  - “会动”大概率指页面动效，不代表复杂应用。
  - 用户没提登录、数据库、后台，所以不默认扩展。
  - 首版适合做 HTML + CSS + JavaScript 静态单页。

## 处理方式

- 下一步：直接执行
- 交付物：一个本地可打开的静态单页网页
- 范围：布局、视觉风格、CSS 动效、少量 JavaScript 交互
- 输出：HTML、CSS、JavaScript 文件
- 不做：账号系统、后台接口、数据库、上线部署
```

### 非专业用户的技能修改

用户：我不懂这些技术名词，但你帮我把这个 AI 技能改好，别让它老是误会我的意思。

规范化：

```markdown
## 用户真实目标

让 AI 在处理模糊请求时更准确理解用户真正想要什么，减少盲目执行和术语化追问。

## 专家视角

- 领域：AI 工作流设计 / 技能文档写作
- 角色：AI 交互设计师 + 技能维护者
- 用户画像：用户明示不懂技术名词，关心最终效果，不应让用户选择实现细节
- 表象翻译：“别误会我的意思”不是让 AI 猜心思，而是增加身份、场景、意图和成功标准的校准规则
- 意图画像：修改 + 执行
- 关键判断：
  - 用户要的是技能变得更会判断真实意图，不是要一份解释。
  - 技术路线应由 Agent 内化，向用户汇报效果和风险即可。
  - 文档应加入可执行规则和示例，而不是泛泛提醒“理解用户”。

## 处理方式

- 下一步：直接执行
- 交付物：更新后的 `SKILL.md`
- 范围：身份画像、意图画像、追问方式、模板和示例
- 不做：让用户选择文档结构、引入新工具、扩展成复杂框架
```

### 非代码想法

用户：我最近总觉得团队协作很乱，你帮我搞一个制度。

规范化：

```markdown
## 用户真实目标

降低团队协作混乱，让任务、责任和沟通节奏更清楚。

## 专家视角

- 领域：团队管理 / 流程设计
- 角色：组织协作顾问
- 用户画像：用户是问题提出者，但不一定已定位原因；需要先收束问题，不适合直接给厚制度
- 表象翻译：“搞一个制度”可能不是先写厚制度，而是找出混乱来源并设计一套轻量协作规则。
- 意图画像：诊断 + 规划
- 关键判断：
  - 直接写制度可能会增加负担，未必解决混乱。
  - 需要先区分混乱来自分工、信息同步、优先级、交付标准还是工具使用。

## 处理方式

- 下一步：先确认问题
- 问题：最常见的混乱是“没人知道谁负责”，还是“大家知道负责但进度经常不同步”？
- 原因：这会决定先设计责任分配规则，还是先设计同步节奏。
```
