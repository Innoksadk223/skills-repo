# 提炼与入库门槛

写正式记录前读这一份。它回答两个问题：**值不值得收**（入库门槛），以及**怎么把一次事故变成可迁移的规则**（提炼）。

## 入库门槛

正式记录必须同时满足：

- **有真实证据**：错误原文、日志或可重复的实测结果，而不是转述或想象。
- **结论明确到能直接执行**：不是「可能是……」，且已按下面「提炼」一节写成规则。
- **已执行验证并确认结果**，或属于**主动验证成功**得出的工具行为、环境限制、项目约束（这类不必先失败一次）。
- **描述可复用的约束**，能改变未来任务的行动。

明确不收：

- 临时进度、任务细节、只对本次对话有意义的中间状态。
- 泛泛的知识、建议或最佳实践，落不到具体触发条件上的。
- 原始日志堆砌、一次性远端故障、网络抖动等无法复现的偶发问题。
- 现有技能文档已经写清的内容。
- 密码、令牌、私钥等敏感凭证；脱敏只是兜底，写之前应主动去掉。

普通 bug 只有在提炼出可复用规则后才值得收。候选不参与 `recall`；转正必须先补足验证——脚本不会替你核实事实。

## 提炼：从事故到规则

只压缩事故经过不算提炼。入库的是**可迁移的操作规则**，不是某次事故的复述。

1. **以行动规则命名**，不以事故命名。「区分操作失败与空结果」是规则，「curl 那次报错」是事故。
2. **保留共同机制，剔除偶然细节**：工具名、路径、版本、具体数值一般属偶发；但决定适用边界或动作的细节必须留下，不能为抽象而丢掉限制条件。
3. **有明确触发条件和可执行动作**，能改变下一次的行动。「谨慎操作」「注意验证」这类口号不收——读者看完不知道要做什么。
4. **概括范围不得越过证据**：只有一个工具的案例，不得写成「所有工具都这样」。机制没弄清就写项目候选、不泛化；同一机制有对照或多案例时才合并成一条；原则性建议与已验证事实分开写。
5. **按共同机制合并**，不是仅按工具名合并；同一工具但根因不同的两条，不硬合并。
6. **正文写规则，验证只留日期与最短证据**，不搬日志原文。把事故缩写成「XX 报错」也不等于提炼。
7. **正式记录与项目约束分开**：跨项目、跨工具可迁移的操作规则写全局；项目长期特有的约束留项目记忆；工具完整使用说明属于技能文档，不重复记一份。

格式示例（只演示写法，不是要记的内容）：

```text
### 区分正常空结果与操作失败
- 适用: 读取、查询、外部调用既可能返回空结果也可能执行失败，需要区分两者时
- 做法: 让成功但为空与执行失败返回不同状态；不要把异常统一捕获成空结果，否则调用方无法判断。根因：两者在调用方需要不同处置。
- 验证: 2026-09-27；AppleScript 缺失文件、空文件与权限不足，实测分别报错，旧写法把三种情况都当成空结果
```

## 不确定时：先写候选

范围或结论未定的经验写项目候选，它不参与任务开始时的读取：

```bash
python3 ~/.agents/skills/capture-gotcha/scripts/add_gotcha.py add \
  --scope candidate --title '可迁移的规则名' --when '触发条件与适用边界' \
  --action '可执行动作' --verified '2026-01-01 最短验证依据'
```
7. **正式记录与项目约束分开**：跨项目、跨工具可迁移的操作规则写全局；项目长期特有的约束留项目记忆；工具完整使用说明属于技能文档，不重复记一份。确有必要的本机限制可以保留，但要写清环境条件，不当成永久常量。
相同问题再次出现且解法稳定后，用唯一关键词转正；转正要求补足证据，不是只把内容挪个位置：

```bash
python3 ~/.agents/skills/capture-gotcha/scripts/add_gotcha.py promote '关键词' --scope project
python3 ~/.agents/skills/capture-gotcha/scripts/add_gotcha.py promote '关键词' --scope global
```
