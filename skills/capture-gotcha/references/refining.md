# 提炼与入库门槛

写正式记录前读这一份。它回答两个问题：**值不值得收**（入库门槛），以及**怎么把一次事故变成可迁移的规则**（提炼）。

## 入库门槛

正式记录必须同时满足：

- **有真实证据**：错误原文、日志或可重复的实测结果，而不是转述或想象。证据是写入前提，只留在事故记录或任务上下文里，不落盘成字段。
- **结论明确到能直接执行**：不是「可能是……」，且已按下面「提炼」一节写成规则。
- **已执行验证并确认结果**，或属于**主动验证成功**得出的工具行为、环境限制、项目约束（这类不必先失败一次）。
- **描述可复用的约束**，能改变未来任务的行动。

明确不收：

- 临时进度、任务细节、只对本次对话有意义的中间状态。
- 泛泛的知识、建议或最佳实践，落不到具体触发条件上的。
- 原始日志堆砌、一次性远端故障、网络抖动等无法复现的偶发问题。
- 现有技能文档已经写清的内容。
- 密码、令牌、私钥等敏感凭证；脱敏只是兜底，写之前应主动去掉。

普通 bug 只有在提炼出可复用规则后才值得收。候选不参与 `recall`；转正前先补足真实证据与明确结论，脚本不会替你核实事实。

## 提炼：从事故到规则

只压缩事故经过不算提炼。入库的是**可迁移的操作规则**，不是某次事故的复述。

1. **以行动规则命名**，不以事故命名。「区分操作失败与空结果」是规则，「curl 那次报错」是事故。
2. **保留共同机制，剔除偶然细节**：工具名、路径、版本、具体数值一般属偶发；但决定适用边界或动作的细节必须留下，不能为抽象而丢掉限制条件。
3. **有明确触发条件和可执行动作**，能改变下一次的行动。「谨慎操作」「注意验证」这类口号不收——读者看完不知道要做什么。
4. **概括范围不得越过证据**：只有一个工具的案例，不得写成「所有工具都这样」。机制没弄清就写项目候选、不泛化；同一机制有对照或多案例时才合并成一条；原则性建议与已确认事实分开写。
5. **按共同机制合并**，不是仅按工具名合并；同一工具但根因不同的两条，不硬合并。
6. **正文只写规则与做法**，证据留在事故记录或任务上下文里，不搬日志原文，也不落盘成「验证」字段；把事故缩写成「XX 报错」也不等于提炼。
7. **正式记录与项目约束分开**：跨项目、跨工具可迁移的操作规则写全局；项目长期特有的约束留项目记忆；工具完整使用说明属于技能文档，不重复记一份。

## 写入格式与内容纪律

每条固定三个字段，顺序不能变：

```text
### 区分正常空结果与操作失败
- 适用: 读取、查询或外部调用既可能返回空结果也可能执行失败，需要区分两者时
- 做法: 让成功但为空与执行失败返回不同状态；不要把异常统一捕获成空结果，否则调用方无法判断。
- 关键词: 空结果 执行失败 异常捕获 状态码
```

- **标题**：可迁移的动作规则名，不写事故名。
- **适用**：≤50 字，写触发条件与适用边界。
- **做法**：≤120 字，写可执行动作；根因只在影响动作时补一句。
- **关键词**：≤40 字，2–5 个检索词，空格分隔；写别人会查的词，例如错误码、工具名、症状、模块名。不要只重复标题。
- **单条**：≤300 字。写不下说明这条该拆，或者根本不该收。
- 字段值必须单行；换行、裸 CR 与 U+2028/U+2029/U+0085 等行分隔符会被拒绝。脚本的硬上限是适用 120、做法 240、关键词 80 字符，上面的纪律更严，按纪律写。

旧五字段与带「验证」的旧三字段仍可读取、照常召回，但不强制迁移；新增记录只接受 `适用`/`做法`/`关键词`，迁移用 `edit --from-entry` 或 `replace`。

## 写前查重

写正式记录前，先用打算写进关键词的词查一遍，再 `inspect` 看现有标题：

```bash
python3 <脚本> recall '错误码' '工具名'
python3 <脚本> inspect --scope project    # 或 --scope global
```

- 已有同义记录：用 `edit '<标题>' --scope ... --expect <version> --keywords '新词'` 改那一条，不新增。
- 确实是新规则：`add --scope project --title '规则名' --when '触发条件' --action '可执行动作' --keywords '词1 词2'`；也可用 `--from-entry <片段|->` 提交完整记录。
- 标题完全相同（忽略大小写与首尾空白）时 `add` 返回 `skipped` 与命中的标题；换标题前先确认它真是另一条规则，否则改用 `edit`。
- 范围拿不准先写候选，不要猜；候选确认后再 `promote`。

## 不确定时：先写候选

范围或结论未定的经验写项目候选，它不参与任务开始时的读取：

```bash
python3 <脚本> add --scope candidate --title '可迁移的规则名' \
  --when '触发条件与适用边界' --action '可执行动作' --keywords '词1 词2'
```

相同问题再次出现且证据稳定后，用唯一关键词转正：

```bash
python3 <脚本> promote '关键词' --scope project
python3 <脚本> promote '关键词' --scope global
```

转正要求补足真实证据，不是只把内容挪个位置；目标已有同标题记录时会跳过并保留候选。
