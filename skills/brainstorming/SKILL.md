# Lightweight Brainstorming

## Purpose

Turn a fuzzy request into a clear next action. The outcome is shared understanding, not a ceremony.

## Trigger Rule

Use this before acting on any request to create, change, design, choose, plan, add functionality, or modify behavior.

The flow can be brief for simple work, but the intent check should still happen. If the request is purely read-only, factual, or already has an approved plan, this skill may simply confirm that no brainstorming is needed.

## Core Flow

1. Restate the likely goal in plain language.
2. List important assumptions.
3. Inspect available context instead of asking when files/tools can answer.
4. Ask one question if the answer changes the route.
5. Offer 2-3 routes with tradeoffs.
6. Recommend one route and explain why.
7. Get approval before file edits, significant time spend, irreversible choices, or scope expansion.

## Question Ladder

Ask only the first question that is still unresolved:

| Need | Question |
| --- | --- |
| Goal | "What outcome should exist when this is done?" |
| Audience | "Who will use or judge this?" |
| Boundary | "What should stay out of scope?" |
| Quality bar | "What would make this feel successful?" |
| Constraint | "Is speed, quality, cost, or reversibility most important?" |

## Mini Design Shape

For small tasks:

```markdown
Goal:
Assumptions:
Recommended route:
Approval needed:
```

For larger tasks, add scope, non-goals, steps, verification, and stop conditions.

## Guardrails

- Do not require a formal spec by default.
- Do not ask a pile of questions at once.
- Do not invent future-proofing the user did not ask for.
- If the user's route looks worse than another route, say so plainly and recommend the better path.
