# UI/UX Prompt Designer 双路线流程设计

## 目标

把 `uiux-prompt-designer` 平移为与 `image-prompt-designer` 同构的双路线流程，同时保留 UI/UX 专属采访维度、implementation / visual 模式、风格 schema 和质量要求。

两条路线都产出可复用的通用 UI/UX 提示词。产品名、品牌标识、具体页面文案、业务数据和单次页面内容只在需求摘要中报告，不进入提示词或风格 JSON。

## 文件边界

- `skills/uiux-prompt-designer/SKILL.md`：路线选择、共用六节模板、冲突处理、风格保存、输出格式和质量检查。
- `skills/uiux-prompt-designer/references/route-a-interview.md`：现有八组字段与逐组采访。
- `skills/uiux-prompt-designer/references/route-b-reverse-ui.md`：仅成品界面图片或截图的规则倒推与单次批量确认。

不引入脚本、状态目录、跨技能引用或新 schema。

## 路线选择

- 只有文字需求：路线 A。
- 指定本地已有风格：加载预填后走路线 A。
- 提供成品界面图片或截图：路线 B。
- 直接要求搭建、修改或审查界面：转交 UI/UX 执行能力。
- 粘贴成品提示词文本并要求倒推：说明不支持，不进入两条路线。

两条路线进入后都先展示共用六节结构，不计为提问。

## 路线 A

保留八组字段：输出目标、产品背景、页面范围、内容数据、品牌风格、视觉系统、体验行为、质量约束。每轮只确认一组，标准流程八轮。implementation / visual 模式继续作为输出目标的一部分。

把具体产品、页面、文案、品牌和数据标记为一次性内容并从最终提示词及风格 JSON 中剔除；其余确认结果进入共用组装。

## 路线 B

仅接受成品界面图片或截图。按相同八组分析可见证据；静态图无法证明的交互、动效、响应式、技术栈、文件边界和可访问性细节保持未指定，或在确有必要时标为 `授权推断` 并说明依据。

先拆分可复用规则与一次性内容，再完成冲突检查和六节草稿。一次展示八组依据、拆分结果、冲突取舍、模式建议、草稿和风格字段摘要，只提出一个批量确认问题。用户在该次回答中给出修正时直接应用，不再追问；拒绝继续时停止。

## 共用提示词模板

最终提示词始终保留六节：

1. `[设计规则]`：视觉系统、布局、色彩、排版、表面和组件。
2. `[体验规则]`：导航、状态、反馈、动效、响应式和可访问性。
3. `[内容规则]`：信息层级、内容密度、真实内容、空态和错误态。
4. `[交付规则]`：implementation 或 visual 模式对应的执行、边界和验收要求。
5. `[禁止事项]`：任务相关反模式和风格冲突。
6. `[任务]`：根据以上规则，为用户提供的产品需求设计或实现界面。

implementation 模式保留现有项目检查、技术栈、文件边界、组件状态、响应式、可访问性、性能和运行验证要求；visual 模式保留设备、视口、构图、关键状态、真实内容和负向视觉要求。提示词不依赖当前对话、本技能或源文件，也不包含角色设定、占位符或与执行无关的元指令。

## 共用尾部

- 保留当前冲突处理、平台规范优先级、减少动效降级和可访问性底线。
- 保持 `schema_version: 1` 及现有全部字段。
- 保留需求摘要、设计方向、UI/UX 提示词、避免事项、验收清单和风格文件；避免事项不重复清单，只说明已并入 `[禁止事项]`。
- 路线 B 的需求摘要列出八组依据、授权推断和被剔除的一次性内容。

## 验证

1. 路线 A 文字化走查：展示模板后完成八组提问，输出六节通用提示词。
2. 路线 B 截图走查：分析阶段零提问、一次批量确认，不触发路线 A。
3. 检查两种模式的专属规则仍存在。
4. 检查风格 JSON 字段与改造前 schema 完全一致。
5. 检查具体产品、品牌、文案和数据未进入提示词或风格 JSON。
6. 使用 skill-creator 验证并运行 `setup.sh`，确认仓库副本与 `~/.agents/skills/uiux-prompt-designer/` 一致。
